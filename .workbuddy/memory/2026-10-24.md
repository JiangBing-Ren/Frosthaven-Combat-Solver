### 新逆向成果（写进了 ATTACK.md §2.1 / §2.2 / §4.1）
- **伤害表达式的精确构造顺序**（`GameState.DrawAndApplyAttackModifierCards` 末尾 +
  `CAttackSummary.CalcExpressionString`）：
  每张抽到的牌按 `MathModifier` 是否含 `*`/`/` 二分；
  加减类进括号内按抽牌顺序累加，乘除类在括号**外**按抽牌顺序左结合，
  **护盾在乘算之后才减**，最后 `Max(0, …)`。
  等价算法：`v=基础; v+=各加减; for 各乘除: v=v OP val; v-=护盾; v=max(0,v)`。
  反直觉点：护盾 1 打 `3*2` 是 `6-1=5`，不是 `(3-1)*2=4`。
  与 ATTACK.md 里 10 条实证表达式逐条对过，全中。
- **一次攻击抽几张**：`while(牌==null||牌.Rolling) Draw()`；
  None = rolling链+终止牌；Advantage = rolling链+二选一；
  **Disadvantage 只留二选一那张（滚动态被丢弃）**。
  优劣势第二张**只翻一张**，不再 rolling 循环。
  劣势特例：第一张是 ×0 时必取它。
- **射程判定不是 HexDist，是寻路长度**：`CAbilityAttack.IsTileWithinRange`
  调 `FindPath(ignoreBlocked:true, ignoreMoveCost:true, ignoreDifficult:false,
  ignoreHazardous:false)` 取 `path.Count <= range`，跨 hex map 还有 DoorPath 拼接。
  ⇒ 求解器照抄这组参数，不要用 `Point.HexDist` 顶替。
- **`CActor.HaveLOS(CTile,CTile)` 是 public static 且纯几何**（与谁站在那无关）
  ⇒ 可直接算**假想站位**的视线。
- **`ScenarioManager.PathFinder` 是 public static**，`FloodFill_ToRange` 的起点可填任意假想坐标
  ⇒ 移动可达集不用自己复刻，地形/门/冰面全交给游戏。
- 护盾读法：`CActor.CalculateShield(cache:false)`（**必须 cache:false**，只读插件不留副作用）。

### 关键设计决定
- 出牌 = 一张出上半边 + 另一张出下半边 ⇒ **n(n−1) 有序对**，先攻取上半边那张的 Initiative。
- 剪枝（否则 16 万方案爆内存）：
  ① 半边有攻击却打不到任何目标的落点直接砍（顺带砍掉整片子树）
  ② 整条链无攻击时站位只留原地
  ③ 可达格 / 射程 / 视线 / BestAttack 全部按 key 缓存，跨出牌组合复用
- **验证不靠感觉**：挂 `GameState.DrawAndApplyAttackModifierCards`（13 参数，返回 Int32）做 Prefix/Postfix 对拍。
  Prefix 时牌堆未动 → 拿到完整牌序；返回值 = 护盾前伤害；out 参数 = 实际用到的牌。
  一次验掉「牌序预测 / rolling / 优劣势 / 加减乘顺序」。
  另打 `基础攻(卡)=X 实际基础=Y 差=Y-X` 观察常驻 buff 偏移（这块模型还没建模）。

### v1.3.0 卡面语义 + 基础动作 + 团队联合规划（用户第四轮实战反馈）

用户四条反馈，主题是 **"先把规则理解对，再谈最优"**。核心事故：求解器把卡面半边
一律当成"移动/攻击动作"，于是推荐出游戏里根本不存在的操作。

**① 常驻加成 ≠ 动作（最关键）**
判据走游戏自己的数据：`CAbility.ActiveBonusData != null
&& Duration != CActiveBonusDurationType.NA` → 这一半是**常驻加成**，不是本回合动作。
（反射读取，跨版本拿不到就静默退化，避免 JIT 阶段炸掉整个插件。）
实证 `100_Deathwalker_StrengthOfTheAbyss.yml`：下半是 `BBuffMove`(Move 2,
Behaviour=BuffMove, Duration=Persistent) + `BBuffAttack`(Attack 2,
Behaviour=BuffSingleAttack, Hidden=True, IsToggleBonus=True, CostAbility=RemoveShadow)。
里的 `Move: 2` / `Attack: 2` 是**加成幅度**（以后每次移动/攻击 +2），
**不是**这一回合能移动 2 格 / 攻击 2 点。之前直接拿它当动作 → 方案不可执行。
新增 `HalfKind { Empty, Action, PersistentBonus }`，只有 `Action` 进入枚举。

**② 基础攻击 2 / 基础移动 2**
任何一张牌都能不当卡面能力用、改当通用基础攻击（攻2/射程1/单体）或基础移动（走2格）。
数值从 `card.DefaultAttackAction` / `DefaultMoveAction` 读 —— **不写死 2/1**，增益和道具会改它。
组合爆炸控制：**只在"该卡至少有一半不是我们建模得出的动作"时才生成基础动作候选**
（空的 / 常驻加成）。两半都正常的牌，玩家不会想拿它当 Attack2 用。
输出每步都写清来源：`打出「X」的【上半】` vs `把「X」当【基础攻击 2】打`。

**③ 跨角色占位协同**
占位按"我行动那一刻"算，不是所有人当前位置：
  先攻更低的队友（先动） → 用它方案的**终点**
  先攻更高的队友（后动） → **当前位置**
  敌人 → **当前位置**（动到哪未知，保守全占）
  盟友/中立/召唤物/倒地 → 当前位置
这一条直接解决「旗矛没考虑 (14,4) 已被先攻更快方案的大棒占据」——
大棒「义无反顾」是"移动+攻击"合并，打完还能用另一张牌再走两步，不会停在攻击位。

**④ 范围攻击站位限制**
`CAbility.AreaEffect != null` → 要先选焦点格、按固定形状铺开，一次打好几个。
单体伤害模型算不准 → **识别出来就不建模**，诊断文本把形状原样给玩家自己摆
（如旗矛「绞肉机」上半 `0,0,G|1,1,R|2,0,R|3,1,B`；G=自己站，R=敌人，**B=盟友必须站**）。

**⑤ 先攻顺序纳入队友方案**
`CPlayerActor.Initiative()` 取 `CharacterClass.InitiativeAbilityCard`，
这张"领头牌"要等玩家出牌才定 → **选牌阶段读出来恒为 0**，
所以之前三个队友在【先攻顺序】里全显示 0，方案也就无从排序。
现在：第一遍各自独立算 → 用**每人方案里先打出的那张牌**的先攻作为该角色先攻 → 按此排序。
怪物标「预测，取自下一张行动牌」，队友标「取自该角色的推荐方案」。

**⑥ 串行两遍法**：按先攻升序逐个重算，重算时
   - 把先动队友的**终点**算进占用集（不是当前位置）
   - 把先动队友预计造成的伤害从目标有效血量里扣掉
   - 重算完把自己的终点 + 伤害累积进去，供后动者使用
输出新增【团队总览】，按先攻先后列出每人用什么半边、终点站哪、伤害击杀。

**★ 三条新教训**
1. **枚举必须一般化**：之前写死"一张牌出上半、另一张出下半"，
   漏掉了 (上,上) 和 (下,下) 这些**合法组合**——方案当然不是最优。
   现在每张牌的候选 = {上半, 下半, 基础攻击, 基础移动}。
2. **剪枝条件里不要混用不同 offset 的结果**：
   我曾用"offset=0 算出的目标集"去剪枝"实际 offset=off1 的分支"，直接把有效方案剪没了。
   → 依赖 offset 的目标集必须在确定 off1 **之后**再取。
3. **空的 List 当"占位"会静默吞掉整个循环**：

### v1.4 出牌规则 + 移动落脚限制（用户第五轮反馈，两个都是我理解错了）

**① 出牌规则：两张牌必须一张上半、一张下半 —— 我上一版改错了方向**
v1.3 我把枚举"一般化"成每张牌可任选上下，理由是"漏掉 (上,上)/(下,下) 合法组合"。
**错**：GH/FH 规则是"一张执行上半、另一张执行下半"，(上,上)/(下,下) 根本不合法。
用了某张牌的上半，这张牌另一半也不能再用，另一张牌的上半同样用不了。
→ 改回**两个槽位**模型：
    上半位候选 = {该牌上半, 基础攻击2}；下半位候选 = {该牌下半, 基础移动2}
    枚举 = 有序对(i出上位, j出下位) × 上位候选 × 下位候选 × 执行顺序(2)
  12 张手牌约 1056 组合，全合法。
  实现：`UpperOptions()` / `LowerOptions()`（原 `BuildOptions()` 已废弃）。
  回归 `PlayRuleTests()`：断言上上/下下/同牌复用方案数均为 0。

**② `CAbilityMove.MoveRestrictionType` —— 移动落脚限制**
```csharp
enum EMoveRestrictionType { None, StraightLineOnly, MustEndNextToObstacle,
                            MustEndOnShadow, MustEndOnSpecificTiles, MustEndNextToEnemy }
```
死行「暗影步法」上半 = `Move: 3, MoveRestrictionType: MustEndOnShadow` + `Attack: 3`
→ 可以"先移动3再攻击3"，但**必须停在阴影格**。
游戏自己的校验（CAbilityMove.cs）：
```csharp
if (MoveRestrictionType.Equals(MustEndOnShadow)
    && !GetTilesInRange(...).Any(x => x.FindPropOfType<CObjectShadow>() != null))
    SetCancelAbilityFlag(cancel: true);   // 没阴影格可停 → 整个能力取消
```
处理策略（保守优先）：
  None → 正常枚举；MustEndOnShadow → 可达格 ∩ 阴影格；
  其余四种 → **只保留原地不动**，诊断写明"未建模"。
阴影格判定照抄官方：`CTile.FindPropOfType<CObjectShadow>() != null`。
新增 `Geometry.IsShadowTile(x,y)` + `P1Context.IsShadowTile` 委托
+ `HandReader.ReadMoveRestriction`（反射读 `CAbilityMove.MoveRestrictionType`）。
可达格缓存键从 (x,y,r) 扩成 (x,y,r,restriction)。

**★ 教训：怀疑原实现"不够一般"之前，先确认那个一般化是否合法。**
我上一版看到"只枚举 (上,下)"就以为是漏了组合，
其实那正是规则约束，我把它"优化"掉了，反而引入非法方案。

### v1.10 修窗口两个交互回归（用户实战反馈）

**1. 收起后无法展开 —— 高度被覆盖**
```csharp
_rect = GUI.Window(...);     // ❌ 全量回填
```
GUI.Window 返回实际绘制 rect。收起时高度 = TitleH+ButtonBarH = 52，
回填后 `_rect.height` 永久变 52；再点「+」时 `h = _rect.height = 52`，
只画得出标题栏+按钮栏空壳 → 表现为"无法展开"。
**修复**：`_expandedHeight` 单独记展开高度；`win` 只回填 x/y/width，
**高度绝不写回 `_rect`**；展开时再把用户拖动调整的高度记进 `_expandedHeight`。
（注意别再写 `if (!_collapsed) _expandedHeight = _rect.height;` —— 那会用旧值覆盖掉用户刚调的高度。）

**2. 鼠标拦截死锁 —— 禁用设备后又用它读位置（严重）**
```csharp
InputSystem.DisableDevice(Mouse.current);        // 禁用
Vector2 p = Mouse.current.position.ReadValue();  // ❌ 又用它读位置 → 冻结
```
设备禁用后不再上报新坐标 → 位置冻结在"进入窗口那一刻" →
IsMouseInside() 永远 true → 鼠标再也没放开。
用户："只要求解器窗口开着，就没法使用鼠标操作游戏。"

**修复**
- 位置改从 **IMGUI 的 `Event.current.mousePosition`** 读（legacy 通道，
  独立于 Input System，DisableDevice 不影响）。
- 判定从 Update 挪到 **OnGUI**（Update 里没有 Event）；
  Update 只留"窗口不可见就放行"兜底。
- **看门狗**：拦截期间位置连续 ~2 秒(120帧)没动 → 强制放行 1 帧。
  万一 Event 也冻结，不会永久锁死；正常阅读时也会触发，但放行无害（不点击就不误操作）。

**★ 设计原则（用户明确，务必遵守）**
> "我们是要鼠标移入求解器窗口以后不误操作游戏……
>   方便玩家一边看方案一边执行操作才是我们做游戏内窗口的主要原因。"
即：**只挡"鼠标压在窗口上"的那一刻，移开立刻放行**；不是接管鼠标。
滚轮拦截也是同理（DisableDevice 会禁掉滚轮，因为滚轮属于 Mouse 设备）。

**教训**：① GUI.Window 返回值不能盲目全量回填（收起态会污染）；
② **禁用某个输入设备后，绝不能再用该设备读状态** —— 必然死锁；
要留存一个不受禁用影响的独立通道（这里是 IMGUI Event）。

### v1.14 P5 精确化：敌人回合接上真实寻路

**动机**：上一版够不着判定是 `dist <= AttackRange + MoveStrength`（纯几何上界），
**会高估** —— 隔一堵墙、或压根没有路，也会被算成"它能打到你"，玩家被吓得不敢站。

**改法**：真的去寻路，看是否存在一个可达格能打到目标。
考虑了**地形**（困难地形多耗移动力，寻路里已含）、**占用**（别的单位挡路）、**视线**（墙）。

**为什么另写 `Solver/EnemyPathing.cs` 而不复用 `Bridge/EnemyPredictor`（P4）**
EnemyPredictor 依赖 CScenario / CActor / Geometry 等**游戏类型**，
而 StateAdvancer 是**纯计算层**（不引用游戏类型，测试台才能直接编译它）。
→ 复刻同一套规则，输入改成**委托**。
`P1Context` 本来就有 `Reachable` / `RangeDistance` / `HasLOS`，
现在 `WorldState` 也带上这三个委托（Clone 时共享引用，委托不可变）。

**复刻的选位规则**（CAIMoveNew，反编译实证，无随机）
```
① 焦点 = 敌对单位中「能打到它所需的移动代价」最小者
② 落点 = 可达格里「能打到焦点」且「移动代价最小」的格子
③ 现在站的格子就能打到焦点 → 它不动（代价 0 已最小）
```

**★ 修掉一个焦点 tie-break 的真 bug（重要教训）**
游戏 `CompareEnemies` 顺序：`lowestMoveCostToAttack 升序 → hexDist 升序 → 先攻`。
我第一版把 tie-break 写成"**落点**到目标的距离" —— **比错了维度**。
正确的是：移动代价相同时，比的是**敌人自己**到目标的距离（hexDist）。

后果很实际：敌人夹在你和队友中间、两边都不用移动就能打到时，
它会打**更近的那个**；比错维度就可能选成打你 → 让你误判要不要躲。
回归用例 ⑤ 抓到这条（队友 (14,4)、我 (14,3)、敌人 (14,5) → 应该打队友）。

**配套行为变化**
- 打不到任何人 → **原地不动，也不抽牌**（真实规则：没出手就不消耗修正牌）
- 打队友时只消耗牌、不掉我血（它确实出手了，牌堆要推进）
- 先动敌人占住新格后，后动敌人**不会踩上去**（占用集随移动动态更新）
- `EnemyStrike` 新增 `Moved` / `FromX` / `FromY`，输出写"走到 (x,y) 后"

**回归 `EnemyPathingTests()` 新增 14 条**：
没有路 → 打不到（旧版会误判）/ 没视线 → 打不到（旧版会误判）/
有路 → 移动后打到你 / 原地能打到 → 不动 / 焦点是更近的队友 / 两敌人不站同一格。

**仍保留的简化**：打不到任何人时它原地不动（真实 AI 可能仍会朝你挪近几格）；
不模拟敌人对我方的优劣势；队友回合不推进。

**状态**：v1.14.0，离线测试台 **139 项断言全部通过**，已部署。

### v1.15 纠正：够不着时敌人**会逼近**，不是原地不动（用户要求查证）

用户要求"调查清楚真实的敌人 AI，不盲目确信打不到人就一定会原地不动"。
**查证结果：我上一版（v1.14）的假设是错的。**

**反编译证据（CAIMoveNew.cs，1975 行）**

`Process()` 主流程：
```csharp
CalculateValidAttackTilesForAllEnemies();
SortEnemyEvals();
var source = enemyEvals.Where(x => x.lowestCostAttackTile != null);
finalFocusEval = source.FirstOrDefault();
if (finalFocusEval?.lowestCostAttackTile != null) {
    FindBestAttackPositionForTheFocus();
    FindPathToFocus();      // ← fallback 在这里
    CalcWaypoints(); ...
}
```

⚠ `CalculateValidAttackTiles` 选 `lowestCostAttackTile` 时**不检查 reachable** ——
只要求：射程内 + 有视线（CheckLoS）+ 可站立（Walkable && !CannotStop）。
→ "有攻击位"几乎总成立（目标周围基本都有格子），`finalFocusEval` 很少为 null。

**真正的 fallback 在 `FindPathToFocus()`**
```csharp
if (bestAttackTile == null || maxMoveCount == 0) { AIMoveFocusPath.Clear(); return; }
pfContext.GetPathTo(bestAttackTile.position, AIMoveFocusPath, maxMoveCount);
if (IsCurrentPathPerfect()) return;         // 走到攻击位 → 完成

// 走不到：在**所有可达格**里挑"离攻击位最近"的走过去
SortAttackTilesAndFindNumberOfBests();
InitReachableTiles();                        // 排除自己脚下
AIMoveFocusPath.Clear();
foreach (reachableTile in reachableTiles) { ... AIMoveFocusPath.AddRange(reachableTile.path); }
```

`IsCurrentPathPerfect` 判"不完美"：终点不是攻击位 **且** 还有剩余移动力
（`CostWithoutTraps(cost.movePoints) < maxMoveCount`）→ 继续贴近，把移动力用掉。

**结论** = GH/FH 标准规则「怪物会尽可能靠近焦点」。
只有两种情况真不动：① bestAttackTile == null（目标被墙封死）
② maxMoveCount == 0（移动力为 0）。**否则它几乎总会移动。**

**★ 我的偏差方向是「低估」，比高估更危险**
旧实现让它"打不到就杵着"，你会**误以为安全**，实际它已挪到你旁边，下回合就能打到。

**修正**
- `EnemyPathing` 新增 `EnemyMovePlan` 三态：Attack / Approach / None
- 够不着 → 走到"离焦点最近的可达格"，**要求必须比现在更近才动**（避免无意义抖动）
- 这回合**不出手、也不抽修正牌**（真实规则：没出手就不消耗牌）
- `EnemyStrike` 新增 `ApproachOnly`，输出提示"够不着你 → 逼近到(x,y)，这回合不会出手"
- 实测：距离 6、射程 1、移动 2 → 逼近到距离 4，牌堆未消耗 ✓

**保留的近似**：贴近目标取"离焦点本人最近的可达格"，
真实代码是"离最佳攻击位最近"（攻击位本就在焦点旁，绝大多数等价）。

**教训（和 v1.4 那条同源）**：
规则性假设不能靠"想当然 + 写进文档"就当真。
我 v1.14 把"打不到就原地不动"写进了文档和窗口说明，
用户一句"不盲目确信"就戳破了 —— **凡是写进玩家可见说明的行为断言，
必须回到反编译代码里找到对应分支，否则宁可标注"未确认"**。
