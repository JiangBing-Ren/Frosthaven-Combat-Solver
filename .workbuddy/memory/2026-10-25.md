
### v1.17 阴影门槛：0 阴影时不能推荐有阴影限制的牌

用户实战："死行方案依旧有问题，怎么上来就又使用有阴影限制的牌？此使命开局并没有任何阴影。"

**两个叠加 bug**（都会导致推荐出根本用不了的牌）

**bug 1：原地不动绕过了落脚限制**
```csharp
// P1Planner.dests() 里
foreach (t in ctx.Reachable(...)) {
    if (restriction == "MustEndOnShadow" && !IsShadowTile(t)) continue;   // 可达格过滤了
    list.Add(t);
}
if (!list.Contains((x, y, 0))) list.Insert(0, (x, y, 0));   // ❌ 但原地被无条件塞回来
```
开局 0 阴影 → 可达格全被过滤 → list 空 → 原地硬塞回来 → 方案生成，落点=当前格（无阴影）→ **非法**。
修复：原地也要过 `IsShadowTile(x, y)`。

**bug 2：压根没有"半边可用性"判定**
之前只要 Kind==Action 就进候选，从不检查前提。
新增 `ShadowRequirementMet(half, ctx)`：
- MustEndOnShadow：当前格不是阴影 **且** ShadowCount==0 → 不可用
- PerformFromShadow：ShadowCount < m_ShadowsToUse → 不可用
⚠ **造阴影类不受此限**（它正是没阴影时的解法，不能自己挡自己）。

UpperOptions/LowerOptions 据此过滤；诊断写明原因（"0/5"、"无法使用"）。

**报告新增【阴影】段**（配置 ShadowDiagnostics，默认开）
开局是不是 0 个直接决定哪些牌能用 → 显示出来对账：
```
【阴影】场上当前 0/5 个
  ⚠ 一个阴影都没有 → 「暗影步法」这类必须停在阴影的牌本回合用不了…
```

**数据读取验证（Geometry.ShadowCount）** —— 反编译核对：
- `ScenarioState.ShadowProps` = `GetPropsThreadSafe.Where(ObjectType == Shadow)`
- `CObjectProp.ArrayIndex` 是 `TileIndex`（有 .X/.Y）
- 游戏自己也是 `CurrentScenarioState.ShadowProps` + `shadowProp.PropTile`
- 排除 `WillBeRemoved`（本回合将被移除的不算）

**回归 ShadowGatingTests() 5 条**：0 阴影不推荐暗影步法上半 / 诊断说原因 /
说"0/5" / **有阴影时可以推荐**（避免矫枉过正）/ 旧用例补 ctx.ShadowCount。

**教训**：① "原地不动永远是个选项" 这种**兜底**最容易绕过前面辛苦做的过滤，
加过滤时要回头检查兜底路径；② 半边可用性 = 不只判断"是不是动作"，
还要判断"**前提**是否满足"（阴影、元素、站位…），这是本次新增的一层。

### v1.18 状态机制建模 + 修掉让阴影过滤完全失效的反射 bug

**★ 最重要的发现：反射打错了类，阴影过滤从未生效**

### v1.19 疑点系统排查 + 反射静态校验（用户要求"用 REA 反编译 / 查清疑点 / 完善模型和测试台"）

**★ REA 实测结论：对 .NET Mono 后端不适用（有证据，不是猜）**

用 MCP 的 REA 打开 Assembly-CSharp.dll，REA 自己判定：
```
{"format":"pe","architecture":"x86",
 "provider_id":"ghidra","code":"managed_target_unsupported",
 "reason":"Windows Ghidra P0 accepts native PE applications and DLLs;
           managed or unclassified PE targets are unsupported.",
 "diagnostics":{"executable_role":"shared-library","managed":true}}
```
四个 provider 全拒：ghidra(managed_target_unsupported + not_configured)、
hopper(unsupported_host win32)、ida(not_configured)、kuna(只认 ELF/Mach-O)。

`"managed":true` 说明 REA **能识别**这是 .NET 程序集，但它的反编译引擎全只做 native。
本项目 Unity Mono，业务逻辑全在托管 DLL → REA 无从下手。
唯一 native 文件 UnityPlayer.dll(31MB) 是引擎本体，无业务逻辑。已 close_binary。
⇒ 继续用既有 C# 反编译产物（decompiled/SRL）作为规则真相来源。

**疑点 ① IgnoreLOS —— 查清并建模（之前会低估）**
SharedAbilityTargeting.GetValidActorsInRange：
```csharp
GameState.GetTilesInRange(..., ignoreLOS: ability.MiscAbilityData?.IgnoreLOS ?? false, ...)
```
默认要视线，个别能力显式关掉。攻略说的"非目标型不用视线"就是这类卡。
加 ActionSnapshot.IgnoreLOS + HandReader.ReadIgnoreLOS。
顺带澄清：EAbilityTargeting.None 只是标记，不是 LOS 豁免 —— 疑点关闭。

**疑点 ② 隐形目标 —— 查清并建模（之前会高估）**
CAbilityFilter.IsValidTarget：
```csharp
if ((!AreActorsAllied(...) & isTargetedAbility)
    && target.Tokens.HasKey(EPositiveCondition.Invisible) && flag != true) → 非法目标
```
默认不能打隐形，只有 MiscAbilityData.CanTargetInvisible 例外。
加 ActionSnapshot.CanTargetInvisible + TargetsFor 排除。

**疑点 ③ 仍不建模（已列「报错」页）**：元素（27 个能力文件，完整子系统）、
陷阱/冰面（CObjectTrap.GetTrapDamage 有接口但需逐个算路径）、召唤物主动召唤。

**★ 新增 tools/verify_reflection.py（构建期静态校验）—— 针对两次静默失败**
v1.17 脚本忘写回、v1.18 反射打错类：都编译通过+测试全绿+部署成功，但实战完全失效。

**★★ patch.py 自身的 bug（第五次同类事故，这次是工具层）**

### v1.26 【迭代 1/N】多样性分桶（学 StS2 的 SearchRouteTraits 泳道）

按"对后续的影响程度"逐步迭代 —— 本轮只做**第 1 项**。

**问题**：只按排序取前 K 个 → 前几名往往是同一路子的变体（同样的牌、同样的落点、
同样打谁），用户看到的 Top-5 像"只给了一个方案"。
实测：纯 top-K 的**前 3 名只有 1 种打法**。

**实现**：每个方案算三个签名
- OffenseSignature：这一轮打哪些目标（GUID 排序拼接）
- PositionSignature：最终站在哪
- UtilitySignature：治疗/阴影/拾取/挨打（展示用，**不参与限流**）

筛选 SelectDiverse：
1. 遍历排序后的方案，**进攻**与**站位**两个维度**各自**限流（每桶最多 perBucket 个）
2. 超出桶容量的存进 overflow
3. 剩余名额按排序补齐（数量不变、**第 1 名永远最优**）

**踩坑**：一开始把三个签名**合起来**判桶（"所有签名都不满才算"），
而 UtilitySignature 对大多数方案都一样（"util:"）→ 第 3 个方案全被挡进 overflow，
补齐后等于**没分桶**。改成**每维度独立限流**才生效。

**效果（离线实测）**
| | 纯 top-K | 分桶后 |
|---|---|---|
| 前 3 名的打法种类 | **1 种** | **3 种** |
| 整体打法种类 | 2 种 | 3 种 |
| 不同落点数 | 2 个 | 3 个 |

配置项 `Solver.DiversityPerBucket`（默认 2，0=关闭）。
回归 DiversityBucketTests()：数量不变 / 前排种类不少 / 整体更多 / 落点更多样 /
**第 1 名与纯 top-K 相同**（多样性不影响榜首）。

**迭代清单（按影响程度排，后续项）**
2. ★★★ 线程让步（Unity 卡顿）—— 需先把"读游戏状态"与"枚举"拆开
3. ★★ 多宽度组合器（BeamWidthPortfolio 共享预算）
