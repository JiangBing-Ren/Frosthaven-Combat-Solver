## 攻击（Attack）机制逆向（同日，产出 ATTACK.md）

三层取证：YAML 数据 + DLL 标识符 + Player.log 真实时序（取样 4996 条表达式）。

### 生命周期（真实日志时序）
选择焦点目标 → 确认攻防双方 → 抽修正牌（带 OverallAdvantage 状态）
→ **表达式求值** → 卡牌战斗日志 → 清场 → ActorIsAttacking → 抽牌演出 ×N
→ LogAttackModifier → 伤害表现 → 结算（护盾/穿透/反击）。

**关键：伤害在"表达式求值"阶段就已算完，抽牌与动画只是后续表现**
→ 逻辑先行、动画后演（联机同步设计）。改动画不影响伤害。

### 伤害公式（表达式 = ( 基础 [±修正] ) [×2 | ×0]）
实证：`((2))→2`、`((2)+1)→3`、`((1)+1)*2→4`、`((2))*0→0`、`((1))*0-3→0`、`((1)-1)→0`、`((10))*2→20`
三条铁律：
1. **乘算最后应用** → ×2 连所有加法加成一起翻倍（桌上玩家常误解）。
2. **×0 直接归零**，后续加减不再产生有效伤害。
3. **下限截断 0**，负值一律归零。

### 修正牌
标准牌组 20 张：+0×6, +1×5, +2×1, -1×5, -2×1, **T0(×0)×1, T2(×2)×1**；怪物牌组构成相同。
T0/T2 自带 `Shuffle: True` → 抽到极端牌立即重洗。
优势/劣势：None 抽1；Advantage 抽2取好；**Disadvantage 抽2取坏**（直接证据：
日志"抽到了 -1 与 +2"，最终取 -1）。

### 隐藏规则
1. **ReducedRandomness 牌组**（数字版特有）：去 ×0/×2，换 P2_Shuffle(+2)/M2_Shuffle(-2)，
   抽到即洗 → 抹平暴击/落空方差。有独立 MonsterReducedRandomness 版本，
   标志 `IsReducedRandomnessDeck`（房规开关，当前未启用）。
2. **护盾是快照**：`CachedShieldValue`；护盾与穿透在 `CalcShieldPierce` 同函数结算。
3. 护盾分类型：`ShieldIncomingAttacks` / `ShieldTargetedAttacks` / `ShieldAndRetaliate` /
   `ShieldAndDisadvantage` → 判定时先匹配类型。
4. 落空仍走完整流程（卡牌照常消耗）。

### 日志关键 grep

`OverallAdvantage status is: None|Advantage|Disadvantage`、
`Drawing attack modifiers`（抽牌）。

## 攻击修正牌机制深挖（产出 MODIFIER.md）

**用户问题**：为什么实际游玩中修正牌像是"固定"的？复原到回合开始重打、或换牌攻击，结果都一样。

### 结论
**抽修正牌不消耗任何随机数** —— `CActor.DrawAttackModifierCard` 直接取 `current[0]`。
牌堆顺序存在存档里，撤销时整份 ScenarioState 被深拷贝回滚 → 重来必定翻出同一张。

### 核心代码证据
- `CActor.cs:4639` `DrawAttackModifierCard`：`current.Count==0` 才洗，然后直接 `current[0]`。
- `AttackModifierDeckState`（ISerializable）：`AttackModifierCardsAvailable` 就是**按翻牌顺序存储**的牌堆。
- `GloomUtility.CopyScenarioState` = `DeepCopySerializableObject<ScenarioState>()`（BinaryFormatter 全量）。
- `ScenarioState` 序列化 4 个 RNG：`ScenarioRNGState`/`EnemyIDRNGState`/`EnemyAbilityCardRNGState`/`GuidRNGState`。
- `Extensions.RandomState` 存 `SharedLibrary.Random` 全量字节（55 槽 + inext/inextp）。
- `RestoreRNGStates()`：四个 RNG 由**同一 int Seed** 重建。
- `SharedLibrary.Random` = **.NET Framework System.Random 的逐行拷贝**（Knuth 减法生成器，56 槽 + 双指针）。
  `RandomSerializationBinding` 把 `System.Random` 重定向到 `SharedLibrary.Random`。

### 日志实证（Player-prev.log）
- `RNG changed from X to Y` **仅 10 次 / 4.5 小时**，全部在场景加载时。
- 真实抽牌 183 次（按 `Drawing attack modifiers. OverallAdvantage` 事件计数）。
- 撤销后立刻重打的**紧邻 4 张完全重复** 3 处；跨 146 次抽牌的 5 张重复块 1 处。
- `CopyScenarioState took 38ms` —— FastUndo 走全状态深拷贝。

### ⚠️ 纠正 ATTACK.md 的错误
原写「T0/T2 自带 `Shuffle: True` → **抽到极端牌立即重洗**」——**错**。
实际是：抽到只**置位** `m_ShuffleAttackModifierCards`，**延到回合末**
（`GameState.cs:4929` `CheckAttackModifierCardShuffle()`）才真正洗。
这是玩家能在一个回合内心算后续修正的基础。

### 隐藏规则
1. 回合末才洗牌；全场只有 2 张牌触发洗牌（T0/T2 或 M2_Shuffle/P2_Shuffle）。
2. ReducedRandomness **不是不洗**，是把 ×0/×2 换成 ±2_Shuffle（保留 2 个洗牌触发器，去掉极端结果）。
3. 初始建堆用**有偏插入洗牌** `Insert(RNG.Next(0,count), item)`，位置区间 `[0,count)` 排除追加到末尾，
   不是无偏 Fisher-Yates；重洗才走 `Extensions.Shuffle()`。
4. ⚠️ **日志里 `*2` 不都是 ×2 牌**：`if (Brittle) text += "*2"` —— 易碎状态也会追加 `*2`，同形。
   `Ward` → `floor(...)/2`。读日志务必注意。
5. `PeekScenarioRNG` = `Save().Restore().Next()`，是**克隆后再取数**，不消耗本体
   → 日志 `[ScenarioRNG] - X` 不代表 RNG 被消耗。
6. Rolling 修正牌会连抽（`while(card==null||card.Rolling)`，上限 200）。

### 对求解器的意义（重大）
**修正牌是确定量，不是随机变量** → 求解器无需算期望，可**精确预知**。
- 读 `CCharacterClass.m_AttackModifierCards[0]` / `CMonsterAttackModifierDeck.m_AttackModifierCards[0]`。
- 本次攻击翻出的牌 = `[0]`；后续 = `[1]`、`[2]`… 可推演 AoE/多目标整串修正。
- 需模拟洗牌时用 `Extensions.Save()/Restore()` 克隆 RNG，在克隆体上跑，不污染真实状态。
- 顺带发现后门：`CAbilityAttack.ConsoleVar_DebugAttackModifierCard`（直接指定翻出的修正牌，调试神器）、
  `CAbilityShowNextAttackModifier`（游戏内已实现"显示下一张修正牌"）。

### 牌组定义（Global/AttackModifierDecks，均为 20 张）
Standard / MonsterDeck：+0×6, +1×5, +2×1, −1×5, −2×1, ×0×1, ×2×1
ReducedRandomness / MonsterReducedRandomness：+0×6, +1×5, +2×1, −1×5, −2×1, −2_Shuffle×1, +2_Shuffle×1

### 工具/方法积累
- ilspycmd 类型清单要带实体类型：`ilspycmd -l c <dll>`（c=class/i=interface/s=struct/d=delegate/e=enum），
  只写 `-l` 会报 "Specify --help"。嵌套类型用 `-t "Ns.Outer+Inner"`。
- .NET 元数据字符串是 **UTF-16LE**，直接 `grep "ASCII"` 会漏；
  要么用 `grep -aoE "[A-Za-z_]+"`（会漏掉纯中文/大写），要么写 Python 做 `decode('utf-16-le')` 扫描。
- 全量反编译便于检索：`ilspycmd -p -o <dir> <dll>`（Assembly-CSharp 11MB 约 2 分钟，产出 1501 文件）。
- 日志行格式 `帧号 (秒) [INFO] ...`，可用来做时间窗口对齐。
- 一次抽牌会把同一条表达式打印约 27 次（4996 / 183），必须先用
  `Drawing attack modifiers. OverallAdvantage` 事件切分，再取该事件后第一条表达式。

## M1 攻坚：Unity 生命周期回调不触发 → 改用 Harmony 挂载（20:30-20:45）

### 现象（v0.2.x）
- 插件组件（BepInEx_Manager 上）与自建 `DontDestroyOnLoad` GameObject 上的组件，
  均只有 `Awake` / `OnEnable` 触发，`Start` / `Update` / `FixedUpdate` / `LateUpdate` **全部不触发**。
- 诊断行确认对象健康：`activeSelf=True activeInHierarchy=True enabled=True hideFlags=None`。
- 95 秒窗口 0 心跳，但 `Time.frameCount` 49270→55695 正常推进 → 主循环在跑、窗口未后台暂停。

### 结论与解法
不要去猜 Unity 消息分发为何不认运行时加载的程序集里的 MonoBehaviour，
**直接挂游戏自己必定被调用的方法**——这是唯一确定能跑在主线程的入口。

实现：`Bridge/TickPump.cs`
- 对 4 个候选 MonoBehaviour 的 `Update()` 打 Harmony Postfix（运行时反射取类型，
  **不编译期引用 Assembly-CSharp**）：
  `Choreographer` / `ClientScenarioManager` / `CharacterManager` / `InteractabilityManager`
- Postfix 取 `__originalMethod` 记录来源；按 `Time.frameCount` 去重，保证每帧只执行一次；
  统计各入口命中次数用于诊断。

实测（v0.3.0 boot，22 秒）：**4/4 挂载成功**，首次心跳来自
`InteractabilityManager`（帧 6467）→ 链路已通。

### 两个已修的代码坑
1. **心跳被功能开关挡住**：原 `if (_owner == null || !Enabled) return;` 在心跳之前，
   诊断信号不可见。已把心跳移到门控之前——诊断信号不该受功能开关影响。

## NPC 行动牌机制调研（2026-10-23，新文档 MONSTER_CARDS.md）

### ★ 结论：行动牌与修正牌同构，完全可预测
敌人/盟友/中立三者都是 `CEnemyActor`，共用 `CMonsterClass` 机制，规则一致。

- `NextAbilityCard => AbilityCards[0]`；`SelectRoundAbilityCard()` 取 `m_AbilityCards[0]`，**零 RNG**
- `SetRoundCard` 会把**同 ID 的重复牌全部移出**牌堆 → 同一张牌不会连续出现
- 洗牌只在一处：`ResetAbilityDeck()` → `m_AbilityCards.Shuffle(EnemyAbilityCardRNG)`
  - 触发条件：① 牌堆空且无 RoundAbilityCard ② 弃掉 `Shuffle: True` 的牌
  - **游戏会把洗牌后完整牌序打到日志**：`"ability deck shuffled:/nAbility Cards:/n<逐张>"`
- `EnemyAbilityCardRNG` 是四个 RNG 之一（SharedLibrary.Random，可离线复刻），**所有怪物类型共用**

### 共享牌池（重要）
- `CMonsterClass` 是**类型级**：同类所有 standee 共用同一张 `RoundAbilityCard`（与桌游规则一致）
- `CardsPoolClass`（YML 配置）可跨类型共享，例：`LadyInWhiteElite` → `CardsPoolClass: IceWraithID`
- `AbilityCards`/`Discarded`/`RoundAbilityCard` 三个属性都转发到 `CardsPoolClass`
- ⇒ **预测粒度是「怪物类型」而非「个体」**

### 先攻恒 0 的根因
先攻值写在行动卡上（`Initiative: 99`），选牌发生在
`CPhase.PhaseType.MonsterClassesSelectAbilityCards` 阶段，此前 `RoundAbilityCard == null`。
⇒ M3 应等选牌完成后采样，不要在此之前读先攻。

### 预测有效期可算
扫描 `AbilityCards` 找第一张 `Shuffle==true` 的下标 i → 还有 i+1 次选牌后洗牌。

### YML
- 怪物类：`StandeeLimit: 8`、`AbilityCards: [770..777]`、`Level0..7` 属性
- 行动卡：`Initiative`、`Shuffle`、`Data.Abilities`

### ⚠️ 更正：先攻「不可知」是错误表述（用户质疑后修正，2026-10-23）
我此前写"先攻在选牌阶段前不可知"，**这是错的**。
正确结论：`Initiative()` 返回 0 只是**阶段门控**造成的"未生效"：
```csharp
if (!flag && card != null && PhaseManager.PhaseType >= CPhase.PhaseType.MonsterClassesSelectAbilityCards)
    num = card.Initiative;
return num + initiativeBonus;
```
`AbilityCards[0]`（=NextAbilityCard）在选牌前就存在，其 `.Initiative` **可读** → 先攻可提前预知。
正确读法：`NextAbilityCard.Initiative + actor.GetInitiativeBonus()`，不要用 `Initiative()`。

**两个会让先攻偏离牌堆预测的例外**（新发现）：
1. `actor.OverrideRoundAbilityCard`：Boss 额外回合脚本
   `BossHasMonsterCardExtraTurnScenarioScript` 会临时覆盖 Boss 行动卡 → 先攻 ≠ 牌堆首张
2. `MonsterClassIDToActImmediatelyBefore`：配置了此字段的类型**跟随另一个类型的先攻**

`GetInitiativeBonus()` = `Class.TempInitiativeBonus` + 所有 `AdjustInitiative` 类 ActiveBonus 之和。

## 战利品袋可挑性追问（2026-10-23，已补入 MISSION_AND_LOOT.md §4.1/4.4）

### ★ 内容何时决定
- `CObjectGoldPile` 是 `CObjectProp` 的**空壳子类**，无内容字段，`AutomaticActivate` 恒 false
  → **袋子本身不存内容**
- 捡拾时走 `TryLootFromDeck` → `CLootDeck.DrawNext(ScenarioState.LootDeck)` → **捡起来那一刻才定**
- 但牌堆顺序由 `CLootDeck.Generate`（按类型分组→每组 Shuffle→按 scenarioLootTable 取量）
  在**进关卡时洗定并持久化** → 第 n 次捡拾的结果进关时已确定
- 捡拾逐格顺序进行：`CAbilityLoot` 遍历 `m_TilesSelected`，每格全部 token 依次抽
  ⇒ 依次拿到 deck[0], deck[1], deck[2]…

### ★ 能否精准挑
**不能跳序挑，但可精准规划**：
- 挑袋子**没用**（所有袋子共享同一牌堆，只影响顺序不影响内容）
- 不能跳序（只能按 deck[0..n] 顺序拿）
- **能精准**：预知 `LootDeck[0..n]` → 决定捡几个、让谁捡
- **唯一的"挑" = LootCardAdvantage**：抽 2 选 1，
  **未选的放回分隔符前**（`AddCardBeforeDelimiter`，下次还能抽到）
  → 可用来"筛选"，把不想要的推后

### RandomItem 不是当场随机
`CActor` 中 `type == RandomItem` 时兑现 **`scenarioSetup.NextRandomItemID`**（关卡预设，可读），
且 `!scenarioSetup.RandomItemLooted` —— **每关只给一次**，之后抽到 RandomItem 退化为金币。
